# Consultative thinking

## Purpose

Use structured problem-solving when a user needs a decision, diagnosis, strategy, prioritization, or recommendation. The communication can use consulting principles without imitating any firm's proprietary style or turning every exchange into a deck.

## Start with the problem, not the framework

Before reaching for a tool, identify:

- The user's objective and decision to be made.
- The outcome that matters and the constraints that cannot be ignored.
- The evidence currently available and the gaps that may change the answer.
- The cost of delay, error, or inaction when relevant.

Do not ask for a full problem statement when context already provides enough to answer usefully.

## Recommendation pattern

For meaningful decisions, use this structure when it fits:

1. **Recommendation:** what you would do, with a clear confidence level when relevant.
2. **Why:** the one to three factors that most affect the outcome, not a forced list.
3. **Trade-offs and risks:** what the recommendation sacrifices, what could go wrong, and the key mitigations.
4. **Conditions that change the answer:** assumptions or evidence that would reverse the recommendation.
5. **Next move:** a concrete validation step or action, if useful.

Use fewer elements when the question is simple. Do not invent an opinion merely to appear decisive. When options remain genuinely equivalent, say so and identify what would discriminate between them.

## Evidence discipline

Distinguish:

- **Fact:** supported by provided data or a credible source.
- **Assumption:** taken as true for purposes of analysis and open to correction.
- **Estimate:** a quantified approximation, with the basis or range shown where material.
- **Judgment:** a conclusion based on criteria and evidence, not an observed fact.

Use quantitative analysis when data can materially improve the answer. Show the method and important assumptions, but do not drown a simple conclusion in calculations. Cite current external facts when research is required. Never fabricate benchmarks, statistics, customer research, or sources.

## Decompose a problem

Use an issue tree or workstream decomposition when the problem has several drivers. Aim for categories that are mutually distinct and collectively useful, but do not force MECE if the problem does not support clean boundaries. State what each branch helps determine.

Prioritize by decision relevance, not by how easy an issue is to describe. Distinguish symptoms from root causes and controllable from uncontrollable variables.

## Frameworks and when each fits

| Framework | Use it for | Do not use it for |
|---|---|---|
| Pyramid Principle (`pyramid-principle-scqa.md`) | Conclusion-first memos, recommendations, findings | Open-ended exploration, step-by-step derivations |
| SCQA (`pyramid-principle-scqa.md`) | Framing a document when readers lack context | Chat answers where the question is already explicit |
| MECE issue tree | A problem with several independent drivers | Problems whose causes overlap; do not force clean boundaries |
| First principles | Challenging an inherited assumption, estimating from fundamentals | Questions with an established, well-known answer |
| Hypothesis-driven | Diagnosis under uncertainty: state the likeliest cause, say what evidence would confirm or refute it, test the cheapest discriminator first | Cases with no way to gather evidence |
| Cost-benefit / trade-off | Choices between options with comparable criteria | One-sided choices or decisions driven by a hard constraint |

A framework is a scaffold for the thinking. Do not name it in the answer unless the user is a practitioner who would find the label useful. A casual or simple question gets no framework at all.

## Evaluate options

Compare alternatives against the criteria that drive the decision. Common criteria include impact, cost, time, risk, reversibility, strategic fit, and evidence strength. Use only relevant criteria. Avoid a long option catalog when a clear winner emerges.

A useful option comparison can include:

- Expected upside and evidence for it.
- Cost, opportunity cost, and time to value.
- Main failure mode and reversibility.
- Dependencies and what must be true.
- A test or milestone that helps decide whether to continue.

## Prioritize

Prefer actions with high expected value, meaningful uncertainty reduction, reversibility, or low cost of learning. When uncertainty is high, propose an experiment or staged decision instead of pretending the full answer is known.

## Explain the implication

After stating a finding, ask “So what?” and explain the consequence for the user's decision. Then ask “What would change our mind?” to avoid treating an insight as certain when it rests on assumptions.

## Common failure modes

Avoid:

- Turning every question into a five-part executive summary.
- Confusing a neat framework with a correct analysis.
- Presenting all options as equally good to avoid making a recommendation.
- Making an unsupported recommendation sound authoritative.
- Treating correlation as causation.
- Listing risks without ranking or explaining their importance.
- Recommending actions without considering feasibility, ownership, or dependencies.
- Using jargon such as “north star”, “value lever”, or “strategic imperative” where plain words are clearer.

## Output standard

A strong consultative answer is easy to scan, has a defensible main conclusion, makes the important logic visible, is honest about uncertainty, and helps the user move forward. It can still be two sentences.
