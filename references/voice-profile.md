# Voice profile

## Purpose

A voice profile captures user-authorized preferences so future writing can become more consistent. It describes observable writing choices and explicit preferences; it is not a psychological profile.

## Four layers

Keep these apart. Each has a different lifetime and owner.

| Layer | What it is | Where it lives |
|---|---|---|
| Global principles | Natural Voice rules that apply to everyone | `SKILL.md` and `references/` |
| User preferences | One person's explicit choices (language, depth, formality, phrases to avoid) | Current conversation, or a host-provided profile the user authorized |
| Project terminology | Product names, jargon, and terms that must not be rewritten | The project's own files, never the user-level profile |
| Context profiles | Voice for a channel (WhatsApp message, design doc, client email) | Derived from the task; may be saved as part of the user profile only if the user asks |

Project terms must not leak into the user-level profile, and one person's preferences must not become a global rule.

## What to capture

Useful fields include:

- Preferred language and locale.
- Formality level by context (casual chat, professional message, technical analysis, public writing).
- Preferred response depth and formatting.
- Word choices, phrases, or formatting the user explicitly likes or dislikes.
- Concrete corrections to previous drafts.
- A short sample the user explicitly identifies as their own writing, when they want voice matching.

## Learning from corrections

Treat explicit corrections as strong signals for the current task. **One correction is not a personality.** Do not infer a lasting preference, or save one, from a single isolated correction. Generalize only when the user says it applies everywhere ("always", "from now on") or the same correction recurs across separate tasks, and even then keep it scoped to the contexts where it recurred. Generalize cautiously: “less formal” in a WhatsApp message does not necessarily mean “less formal” in a legal memo. A preference should be applied across contexts only when the user states that it is global or repeated evidence supports it.

Do not infer style from a text the user wants rewritten; that text may have been written by someone else or generated by a model. Only use a sample for voice matching if the user says it represents their own writing or otherwise authorizes that use.

## Persistence and consent

A skill does not create persistent memory automatically. Store a profile only if the host supports user-approved file persistence and the user has authorized it. Otherwise, use preferences in the current conversation and explain the limitation if asked.

If creating a local profile file, keep it separate from the general skill rules, make it easy to inspect, edit, and delete, and exclude it from source control by default. Do not store sensitive personal information, inferred sensitive traits, private conversation details, or unrelated facts. Prefer style descriptions over raw conversation history.

## Example profile

```yaml
language: es-MX
preferences:
  general:
    - "Direct, natural, warm without excessive reassurance"
    - "Answer the question before giving context"
    - "Avoid generic closing phrases"
  professional_messages:
    - "Polite and concise, not overly formal"
  technical_explanations:
    - "Keep exact technical terminology and show practical implications"
formatting:
  - "Use bullets when they improve scanning, not by default"
  - "Keep lists short unless completeness matters"
```

This is an illustrative template, not a profile to assume for every user.
